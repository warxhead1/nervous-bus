# board — the total board across every project

Federates 10 project beads DBs (`app_to_market`, `biz_worthy`, `deer_flow`,
`hearth`, `` `hearth-loom` ``, `nervous_bus`, `sweepers_adventures`,
`temple_stuart_accounting`, `tengine`, `unreal_battlebots_gamedev` — all on one
dolt SQL server, `127.0.0.1:39502`, data_dir `/home/eric/.beads/dolt`) with
live orca dispatch state and hearth-loom PR lifecycle into one JSON contract
and one human kanban. Motivation: `bd ready` only ever sees one project's DB,
and neither bd nor orca is aware the other exists — a bead can look "ready" in
beads while an orca worker is already grinding on it, or "in_progress" while
its worker died hours ago with no lifecycle event to say so. This closes that
gap in one place.

## Architecture

```
beads_global.all_issues / all_dependencies  (federated SQL views, create_view.sql)
      │  pymysql over dolt's MySQL-protocol port
      ▼
orca orchestration.db (sqlite, mode=ro)  ──┐
      │ tasks.spec bead extraction         │
      ▼                                    │
Redis nbus:* streams (orca lifecycle,      │
  hearth-loom PR + generic lifecycle)  ────┤
                                            ▼
                                       board.py
                                            │
                    ┌───────────────────────┴───────────────────────┐
                    ▼                                                ▼
   ~/.cache/nervous-bus/board/board.json          ~/.cache/nervous-bus/board/report.md
   (FROZEN machine contract)                       (human kanban, one section per lane)
```

## Layer 1 — the SQL views (`create_view.sql`, generated by `viewgen.py`)

`beads_global.all_issues` UNIONs the `issues` table of all 10 project DBs,
adding a literal `project` column mapped to the repo-facing kebab-case name
(`nervous_bus` → `nervous-bus`, `` `hearth-loom` `` stays `hearth-loom`).
`beads_global` itself is excluded — it is the federation/routing DB, not a
project with its own work queue, and including it would double-count.

`beads_global.all_dependencies` UNIONs every project's `dependencies` table.
It exists because each project DB's own `blocked_issues` view only exposes a
`blocked_by_count`, not the blocking ids — board.py needs the raw edges to
populate `blocked_by`.

**`create_view.sql` is a generated artifact. Do not hand-edit it.**

### Why it is generated

bd >= 1.2 migrates a project's `dependencies` table from `depends_on_id` to
`depends_on_issue_id` / `depends_on_wisp_id` / `depends_on_external`. The
migration is **lazy and per-DB** — it runs when the first bd 1.2 client
touches that DB — so the fleet stays mixed indefinitely, and the arms have to
differ per project.

Hand-maintaining that was tried and failed. The 2026-08-31 snapshot recorded
which DBs were on which schema in a comment and asked the next human to move
an arm when a DB migrated. `deer_flow` then migrated, its arm still said
`depends_on_id`, and dolt rejected the **entire** view:

```
(1105, "View 'beads_global.all_dependencies' references invalid table(s) or column(s) ...")
```

One stale arm takes `blocked_by` down for all ten projects at once, and
board.py's run dies with it. So the arms are now derived from each DB's live
`information_schema` shape instead.

### Design rules

| Rule | What it prevents |
|---|---|
| **Explicit roster** (`viewgen.ROSTER`), never `SHOW DATABASES` | A new DB silently joining the total; `beads_global` double-counting itself |
| **No silent omission** — a missing DB/table raises | A view that applies cleanly while a whole project vanishes from the board |
| **Unknown shape fails closed** (`UnknownSchemaError`) | Guessing an arm for a hybrid/partial schema and emitting wrong edges |
| **Safe quoting** — every identifier backtick-quoted, backticks doubled, control chars rejected | `hearth-loom` (a real, hyphenated DB name) breaking generation |
| **Counts + edge identity preserved** | Wisp/external edges disappearing; a wisp id colliding with an issue id and fabricating a blocker |

`all_dependencies` normalises both variants to one shape:
`issue_id, depends_on_id, depends_on_kind, type, created_at`. `depends_on_id`
is the `COALESCE` of the split trio, so **no edge is dropped** from the union;
`depends_on_kind` is `issue` | `wisp` | `external` | `unknown`, so the three
target kinds stay distinguishable. board.py joins only `depends_on_kind =
'issue'` rows to `all_issues`.

### Regenerating, previewing, applying, rolling back

```bash
# 1. Verify the checked-in artifact matches its pinned fleet state (offline,
#    no dolt server needed -- this is also asserted by the test suite).
python3 viewgen.py --check

# 2. Read-only live preflight: probes EVERY arm individually, dry-runs the
#    exact generated union with LIMIT 0 (no DDL), reports snapshot drift, and
#    compares the deployed views' row counts to the sum of their sources.
#    Exit 0 = healthy, 1 = something needs applying. Never writes.
python3 viewgen.py --preflight          # add --json for machine-readable
```

Per-arm probing is the point: dolt reports a broken federated view as one
opaque error naming no arm, so running each arm alone is the only way to learn
which project drifted.

```bash
# 3. If preflight reports drift, regenerate and update the pinned state.
#    (PINNED_VARIANTS in viewgen.py records the fleet snapshot; update it to
#    match --preflight's findings, then:)
python3 viewgen.py --emit > create_view.sql
python3 viewgen.py --check              # must now pass
python3 -m pytest . -q

# 4. PREVIEW the exact statements before applying anything.
python3 viewgen.py --emit --live | diff -u create_view.sql -   # live vs pinned
git diff create_view.sql

# 5. CAPTURE THE ROLLBACK ARTIFACT FIRST -- this is the only copy of the
#    currently-deployed definition.
dolt --data-dir /home/eric/.beads/dolt sql -q \
  "SHOW CREATE VIEW beads_global.all_issues" -r csv       > /tmp/rollback_all_issues.csv
dolt --data-dir /home/eric/.beads/dolt sql -q \
  "SHOW CREATE VIEW beads_global.all_dependencies" -r csv > /tmp/rollback_all_dependencies.csv

# 6. Apply (idempotent, CREATE OR REPLACE, safe to re-run).
dolt --data-dir /home/eric/.beads/dolt sql < create_view.sql

# 7. Re-preflight. Both views must report parity `ok`.
python3 viewgen.py --preflight
```

**Rollback.** Both statements are `CREATE OR REPLACE VIEW`, so rollback is
re-applying the previous definition — either the captured `SHOW CREATE VIEW`
text from step 5, or `git show <sha>:adapters/board/create_view.sql`. Two
caveats:

- Rolling back to a definition that predates a DB's migration restores a
  **broken** view, not a working one. Verify with `--preflight` after any
  rollback rather than assuming the previous state was healthy.
- These are views over live tables. Replacing them touches no rows and is not
  a data migration; nothing in this adapter ever writes to a project DB.

## Layer 2 — the aggregator (`board.py`)

Each run:

1. Queries `beads_global.all_issues` + `all_dependencies` over dolt's
   MySQL-protocol port via `pymysql` (one round trip, not N `dolt sql -q`
   subprocess spawns).
2. Opens orca's `orchestration.db` **read-only** (`mode=ro` — board.py never
   writes orca state). Extracts a bead reference from each `tasks.spec`/
   `task_title` using the exact same regex convention as orca's own
   `src/main/runtime/orchestration/nbus-emit.ts` `extractBeadId()`
   (`[bead:<id>]` tag, else loose `bead <id>` prose), then joins to that
   task's most recent `dispatch_contexts` row for state + heartbeat.
3. Samples the last ~200 entries of orca's worker-lifecycle stream
   (`nbus:orca.worker.lifecycle.v1`) and hearth-loom's PR + generic lifecycle
   streams via `XREVRANGE`. PR-event stream naming is **not** consistent
   between the checked-in schema files and what has actually been observed
   live (see comments in `board.py` — `PR_STREAMS`); all known variants are
   read, none assumed canonical.
4. Derives a lane per issue (precedence `in_flight > in_review > blocked >
   in_progress > ready`, `done_7d` handled first since closed excludes
   everything else) and a `score` (`priority_weight * log2(2 + age_days) *
   1.5-if-blocked`), then writes both outputs atomically (tmp + rename).

### Output contract (`board.json`) — FROZEN

Two sibling lanes code against this shape. Only additive optional fields may
be introduced; existing keys/types never change:

```json
{
  "generated_at": "2026-08-30T18:00:00Z",
  "lanes": ["ready", "in_progress", "in_flight", "in_review", "blocked", "done_7d"],
  "issues": [{
    "id": "...", "project": "...", "title": "...", "status": "...", "lane": "...",
    "priority": 2, "issue_type": "...", "assignee": null,
    "created_at": "...", "updated_at": "...", "age_days": 3.2, "score": 12.4,
    "blocked_by": [], "orca": null, "pr": null
  }],
  "summary": {"per_project": {"nervous-bus": {"ready": 3}}, "per_lane": {"ready": 10}}
}
```

## Tests

```bash
python3 -m pytest . -q
```

All external I/O (dolt/pymysql, orca sqlite, redis) is stubbed with fixture
data or exercised against a throwaway temp sqlite file — never a live dolt
server or real orchestration.db.

`test_board.py` covers bead-id extraction (mirrors orca's regex exactly),
lane-precedence derivation, scoring, the orca sqlite join (including "latest
dispatch context wins" when a bead is referenced by more than one task),
PR-event "most recent across naming variants wins", and the `board.json`
contract shape (exact top-level + issue key sets).

`test_viewgen.py` covers generation and preflight. Where a string assertion
would prove nothing, the **generated SQL is executed for real** against
in-memory sqlite with the roster DBs `ATTACH`ed — sqlite accepts the same
backtick quoting and schema-qualified names dolt does, so a mixed-fleet union
can be run and its rows counted offline. Two scenarios drive it, because they
are the two that actually broke production:

- **Mixed fleet** — both `dependencies` variants coexisting: the union
  executes, every project contributes its rows, the total row count is
  preserved exactly, and wisp/external/all-NULL edges survive with the right
  `depends_on_kind`.
- **Second migration** — one more DB flips `legacy` → `split` after the
  snapshot was pinned (exactly what `deer_flow` did). Regeneration must detect
  it from column shape, change **only** that arm, keep the arm count and every
  project, preserve counts, and have `--preflight` report the drift by name.

Plus: fail-closed on hybrid/partial/missing schemas, no-silent-omission,
safe quoting, determinism, `create_view.sql` matching its pinned state, and
board.py's `preflight_board_views` rejecting an unqueryable, mis-shaped, or
arm-dropped view.

## Known limitations (exhaustion notes)

- **`blocked_by` join is simplified relative to each project DB's own
  `blocked_issues` view.** That view excludes blockers whose status is in a
  per-project `custom_statuses` category of `done`/`frozen`, in addition to
  `closed`. `all_dependencies`/`all_issues` here use `blocker.status !=
  'closed'` only, since `custom_statuses` is not uniformly populated across
  all 10 DBs and resolving it generically would require a per-DB special
  case this adapter does not currently have data to justify. Read-only
  surfaces checked: `beads_global.custom_statuses` (present, categories
  columns exist) but not cross-checked row-by-row against every project DB's
  actual custom status set within this dispatch's time budget. Practical
  effect: a bead blocked only by a `frozen`-category blocker would show as
  blocked here when the project's own `bd ready` would already consider it
  unblocked — false-blocked, not false-ready, so it errs toward
  under-promising availability, not over-promising it.
- **The `blocked_by` join now excludes `wisp` and `external` dependency
  edges** (`depends_on_kind = 'issue'`). Those edges are still in
  `all_dependencies` — the row count is preserved — but they cannot resolve to
  a row in `all_issues`, so they were never contributing a blocker anyway;
  the filter makes that explicit and removes the chance of a wisp/external id
  colliding with an issue id. Live counts checked 2026-09-06 across all 10
  DBs: 3,083 dependency rows total. Not checked within this dispatch: whether
  any `wisp`-targeted edge is semantically a blocker that a future board
  should surface as a distinct lane — that is a product question, and the
  `depends_on_kind` column is there so it can be answered without another
  schema change.

- **`viewgen.PINNED_VARIANTS` is a snapshot, and snapshots go stale.** It
  records the fleet's `dependencies` variants as of `PINNED_AT` so `--check`
  and the test suite work offline with no dolt server. It does NOT detect a
  migration on its own — `--preflight` does, by reading live
  `information_schema`. Run `--preflight` before trusting the checked-in
  `create_view.sql` against the live server; a drift line there means
  regenerate and re-apply.

- **`nbus:orca.worker.lifecycle.v1` was empty at authoring time** (0 events,
  despite a live schema at `schemas/orca.worker.lifecycle.v1.json` describing
  it) — orca is not currently emitting to it. board.py still queries it
  (an empty/nonexistent stream XREVRANGEs to `[]`, not an error) since this is
  a live-system emission gap on orca's side, not a reason for board.py to stop
  reading the source it's documented to use.
